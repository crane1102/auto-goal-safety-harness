# Agent 最让人抓狂的断点：明明是多轮任务，却每次做完一轮就停

## 一个值得公开测试的 Auto-Goal Safety Harness

很多人使用 Agent 时，真正被打断的不是它不会做，而是它只做完第一轮就停下来。

用户明明交代的是一个包含多个步骤的任务：先调查，再整理；先修改，再测试；先生成结果，再检查和交付。Agent 完成第一轮后，却把任务当成已经结束，停下来等待下一条指令。

接下来用户只能再次提醒：“继续。”有时还要重新下一个 goal 指令，告诉它接下来该做什么。任务本身没有结束，执行链却断了。

这不是普通的回答质量问题，而是**多轮任务无法自动识别和持续推进**的问题。

最近公开的 **Auto-Goal Safety Harness**，正是从这个痛点出发：先判断当前输入是否明确包含需要持续推进的多轮任务，再决定是否进入隔离模拟，而不是每次都把一条复杂任务当成单轮问答。

## 它解决的第一个痛点：不必每一轮都重新催促

典型的多轮任务通常包含多个连续动作：规划、执行、测试、复核、交付。第一轮完成，只代表一个阶段完成，不代表整个任务已经结束。

如果系统不能识别这一点，就会出现一种很低效的工作方式：用户不断充当“人工续航按钮”，每完成一轮，就重新发一次“继续”；如果涉及 goal，还要额外下达下一轮指令。

Auto-Goal Safety Harness 的核心方向，就是在当前显式输入中识别这类持续任务候选，例如同时出现多个行动步骤、验证要求、交付要求或明确的后续动作。判断结果不是直接接管系统，而是先给出一个保守的候选信号，再经过显式执行闸门决定是否模拟。

它解决的不是“让 Agent 永远不停”，而是让系统有机会识别：**这件事还没做完，当前只是中间阶段。**

## 它解决的第二个痛点：多轮识别不能以系统稳定为代价

自动续行听起来简单，真正危险的是把错误状态当成任务进度。

因此这个项目不读取历史 session，不调用 native GoalManager，不创建 continuation，不写入 pending event、queue 或 lock，也不修改正式配置。它只处理当前显式传入的文本和 metadata，把实验机制放在独立环境中。

如果 metadata 中出现 `continuation_id`、`pending_event`、`queue`、`lock`、`goal_id`、`task_id`、`wake_event` 或 `resume_token` 等内部状态标记，分类器会保守拒绝，不把它们当成可以自动恢复的依据。

这条边界很重要：系统可以暂时没有识别出多轮任务，但不能因为一次误判，恢复一段不应该恢复的旧执行链。

## 它解决的第三个痛点：异常时不要把普通消息一起拖住

自动判别机制本身也可能遇到异常：输入格式不对、审计失败、模拟状态异常，或者进程意外退出。

项目采用 fail-open 思路。发生异常时，放弃本次自动目标判断，让普通消息继续走原来的路径。也就是说，自动化能力可以这一次没有效果，但不能因为自动化模块出错，就让宿主系统卡住。

对于持续执行系统来说，这比“任何情况下都必须继续”更可靠。真正安全的自动续行，不是永不停止，而是知道哪些情况可以继续，哪些情况必须放弃。

## 这个结果应该怎样理解？

17 个测试通过，证明的是这个独立 harness 当前的分类和安全边界，不等于 native GoalManager 已经安全，也不等于自动续行已经适合直接上线。

它真正的价值，是把一个经常被用户手动补救的问题，变成可以公开测试的机制：

- 复杂任务是否能被识别为多轮候选；
- 第一轮完成后是否仍然保留继续推进的可能；
- 误判时是否会安全放弃；
- 异常退出后是否会避免恢复旧状态；
- 普通消息是否不受影响。

更多测试者可以继续补充真实案例：哪些表达明确说明任务还没结束？哪些表达只是普通的单轮请求？什么时候应该继续，什么时候必须停下？

## 为什么值得继续关注？

Agent 的下一步竞争力，不只是单轮回答更准确，而是能不能把一个真实任务完整走完。调查、整理、修改、测试和交付，本来就是一条执行链。如果每轮都要用户重新按一次“继续”，所谓自动化就仍然把调度工作留给了用户。

但自动续行不能靠盲目恢复状态来实现。它需要同时具备两种能力：识别多轮任务的意图，以及在证据不足时安全停止。

Auto-Goal Safety Harness 目前不是一个宣称已经完成的产品，而是一个相对克制的公开实验起点：先验证多轮任务自动判别，再验证隔离、fail-open 和生命周期边界，最后让更多人通过下载、修改和增加反例来推动它改进。
